# 汽车软件问题排查（Kill-Issue）

把一次"汽车控制器软件问题"的排查固化为标准流程：初始化并规整上下文 → 收集输入并自动生成问题描述 → 澄清提问 → 判定归属层 → 定位证据 → 选模板、出报告 → 登记台账。**一个问题处理完、登记完，再处理下一个**（001 → 002 → 003 …）。

## 一、工作区结构约定

先读 [references/context-layout.md](references/context-layout.md) 了解标准目录结构。核心三条：

1. **通用上下文文件夹**（编号 `000_Context/`；已有工程如 `ModelandCode_SOP_3/` 本身可视为上下文）：所有问题共享的静态材料，按类别分子目录：控制模型、生成代码包、需求文档、接口表、ARXML/DBC、标定数据、测试环境说明、日志。
2. **问题文件夹**：`001-问题精确描述/`、`002-…`、`003-…`（三位序号 + 标题），与上下文文件夹平级。内含 `问题描述.md`（**由排查 agent 自动补全，工程师无需填写**）、`附件/`（logs、CANoe/CANape 报文、截图——**该问题的专属上下文，只用于该问题**）、`证据/`（排查过程截图、代码摘录）、报告文件。
3. **问题台账**：`问题清单.md` 放在项目**最外层**，汇总所有问题状态；每完成一个问题就登记一行。

初始化脚本：`python scripts/init_context.py <项目根> [--issue "001-标题"]` 可一键创建上下文目录、台账和问题文件夹；`--organize` 可对散放文件做启发式归类（见第五节）。

## 二、排查总流程（按序执行）

### 第 0 步：初始化并规整通用上下文（必须）

1. 找到或创建通用上下文文件夹（编号 `000_Context/`；已有工程如 `ModelandCode_SOP_3/` 视为上下文，不强制改名）。
2. **规整（初始化动作）**：用户放入的通用上下文命名不规整时，主动按类别归类到 `000_Context/` 的子目录（01_Model / 02_Code / 03_Requirement / 04_Interface / 05_Calibration / 06_Test / 07_Logs），移动后报告归类结果；不确定类别的文件问用户，不擅自挪动。
3. **对照 context-layout.md 的清单检查上下文（分级，不需要 7 类给全）**：
   - **必须**：模型（01_Model）、生成代码（02_Code）；
   - **条件必需**：DBC/接口表（04_Interface）——只要问题附件里有 log/报文（CANoe .asc/.blf、CANape .mf4/.dat 等），就必须有 DBC，否则报文无法解析成信号；
   - **按需**：需求（03_Requirement，需求存疑/归因需要时）、标定（05_Calibration，标定/数值类问题需要）、测试说明（06_Test，区分测试问题需要）、共享日志（07_Logs，可选）。
4. **缺必须/条件必需的材料就明确提醒用户补**，说明为什么需要（例如"定位显示/状态类问题需要生成代码和模型 SLX 交叉验证，当前只有代码没有模型，请提供"；"附件里有报文但缺 DBC，报文解析不了，请提供"）。**按需材料缺失不阻塞**，排查中需要时再向用户要。
5. **冲突仲裁**：上下文材料之间互相矛盾时，**以模型和代码为准**（它们是"实现真相"，优先级最高）；模型与生成代码不一致时，以生成代码（实际刷写软件）为准；需求/接口表/ARXML/DBC/标定/日志与实现冲突时，以模型和代码为准，并把冲突点记入报告的"遗留确认点/证据差异"小节。

### 第 1 步：收集输入并自动生成问题描述

工程师的输入方式（不需要填任何表单）：
- 在输入框用自然语言描述问题（一句话即可，如"XX 模式下某执行器开度很小调不了"）；
- 把问题文件（logs、CANoe/CANape 报文、截图、trace）放入问题文件夹 `附件/` 或直接拖入对话。

**自动补全**：从输入中提取信息，生成/更新问题文件夹里的 `问题描述.md`（现象/预期/复现条件/环境版本/附件清单/变更背景）；提取不到的信息标记"待确认"，在第 2 步澄清提问中补齐。
- `附件/` 是**该问题的专属上下文**，只用于当前问题，不进入通用上下文。
- 日志解析方法见 [references/log-reading.md](references/log-reading.md)。

### 第 2 步：澄清提问（动手排查前必须完成）

用 ask 工具一次性问清所有疑问点，不要边查边猜。必问清单：

1. **现象与预期**：实际行为和期望行为分别是什么？差异点在哪。
2. **复现条件**：什么工况下出现（模式、温度、车速、档位、是否 5S/6S 等配置）、复现步骤、是否必现。
3. **环境与版本**：HIL / MIL / 台架 / 整车？软件版本、模型版本、构建时间（报告里要写）。
4. **附件说明**：logs/截图/报错在哪个文件、什么时间段、关键信号名。
5. **变更背景**：这个现象是新引入还是一直有？最近改过模型/标定/需求吗？
6. **报告形式**（若用户未指定）：按下面的推荐规则给出默认选择并让用户确认。

> 用户如果已经给全信息，则不重复提问，只确认报告形式。

### 第 3 步：判定问题归属层（报告必有章节）

按证据把问题归类到五层之一（可多选主次）：

| 归属层 | 典型证据 |
|---|---|
| 模型 | SLX 内逻辑错误：错误的条件判断、增益/查表/使能接错、状态机转移条件缺失 |
| 软件 | 生成代码或手写代码缺陷、配置（Configure_* 分支选错）、标定参数错配、构建问题 |
| 测试 | 测试用例激励错误、测试环境（HIL 模型、总线仿真）问题、测量/记录错误 |
| 需求 | 需求文档本身定义不清、自相矛盾、或实现与需求不一致但需求有歧义 |
| 其他 | 面板/外部控制器联动、整车集成、供应商组件、总线通信问题 |

判定依据必须写进报告：对比"实现（模型/代码）"与"预期（需求/标定/产品意图）"，差异在哪一侧。

### 第 4 步：定位证据（四类证据，按需使用）

- **代码证据**：定位到文件 + 行号，摘出问题代码块，**逐块加中文注释说明业务含义**（不是抄代码，是解释这段在干什么）。
- **模型证据**：给出子系统定位路径（模型名 / 子系统层级 / 子系统名），能自动截图就截图（有 MATLAB 时打开 SLX 定位；截图放 `证据/` 并在报告引用），不能截图则留占位并给出精确定位描述。
- **需求/接口证据**：引用需求文档章节、接口表信号定义、ARXML/DBC 报文与信号定义，说明"规定是什么、实现是什么"。
- **日志证据**：时间线、关键信号变化、报错码，截图或摘录并标注时间段。

排查方法套路（输入链路反推、控制链闭环、配置差异等）见 [references/debug-methods.md](references/debug-methods.md)。

### 第 5 步：选模板、出报告

- 报告文件按类型命名，写入问题文件夹：`根因分析报告.md` / `通用排查报告.md` / `5W分析.md` / `8D报告.md` / `定位简报.md`。
- 模板见第四节，写作必须遵守第三节硬性规范。

### 第 6 步：登记台账（每完成一个问题立即登记）

把问题登记进项目**最外层**的 `问题清单.md`（编号、标题、状态、归属层、结论一句话、报告文件路径），**当前问题登记完再处理下一个问题**。

## 三、报告写作硬性规范（必须遵守）

1. **语言**：人类工程师能直接读懂的**结构化逻辑语言**。先讲对象和机制（自然语言 + 表格/流程图），再给证据；不要一开始就堆中间信号名（**通篇堆信号名是头号违禁项**，见第 4 条）。
2. **结论先行**：报告开头一句话结论 = 结论 + 根因 + 触发机制一句话。
3. **图文并茂**：每个关键机制配表格或流程图（mermaid 或干净 ASCII，层次清晰）；模型/日志证据用截图。截图占位格式：`![图N 说明（模型路径/子系统定位）]`。
4. **禁止信号名堆砌（头号禁令）**：报告主体不允许用软件/模型内部信号名、中间量（如 `Switch2_jh0`、`LogicalOperator1_dg`）当证据链——人类工程师看不懂；信号名出现必须配语义翻译（见第 6 条）。同时避免 `***`、`★★`、`★` 等星号装饰、乱码符号、无业务含义的装饰、情绪化表述。
5. **代码块规范**：必须有文件路径 + 行号引用，逐块中文注释解释业务语义。
6. **信号名规范**：信号名/中间量不是不能出现，而是**必须配语义翻译**（示例：空调项目的 `Switch2_jh0` = "A/C 键按下检测结果"），并保留行号作复核索引；语义翻译用人类工程师能懂的业务语言，不用代码语言复述。
7. **归因方向准确**：下结论前先确认因果链方向（谁触发谁、哪一侧先变），方向不确定的点写入"遗留确认点"而不是猜。
8. **分层机制**：复杂因果链按层拆解，每层一个小节、只讲一件事，层间用箭头串起来。
9. **证据索引**：报告尾部放证据索引表（环节 / 语义 / 位置三列），给复核的人。

## 四、报告模板（用户可选，按问题特征推荐）

| 报告形式 | 适用场景 | 模板文件 |
|---|---|---|
| **根因分析报告（默认推荐）** | 控制逻辑、状态/模式、显示、通信类问题的完整技术排查（结论速览 → 机制分层 → 证据索引 → 修复建议） | [report-rootcause.md](references/report-rootcause.md) |
| **通用问题排查报告** | 任何类型问题的**正式完整交付**（对外汇报、项目总结、跨部门流转），覆盖面最全：含调查时间线、影响面与严重度、方案与验证、术语与附录 | [report-general.md](references/report-general.md) |
| 5W 分析 | 责任归属有争议、需要把事实与责任方摆清楚的场合 | [report-5w.md](references/report-5w.md) |
| 8D 报告 | 量产质量问题、供应商问题、需要完整纠正流程的场合 | [report-8d.md](references/report-8d.md) |
| 轻量定位简报 | 只想知道"问题在哪一层 + 关键证据"，一页内出结论 | [report-brief.md](references/report-brief.md) |

**默认推荐规则**（用户未选时）：
- 状态/模式/显示类、控制逻辑类 → **根因分析报告**
- 需要正式完整交付/对外汇报、问题跨多个层面 → **通用问题排查报告**
- 涉及多部门责任归属、归因争议 → **5W 分析**
- 量产/供应商/重复发生的质量问题 → **8D 报告**
- 只是快速确认问题层、时间紧 → **轻量定位简报**

选了模板就严格按模板结构输出，不混用。

## 五、初始化脚本

`scripts/init_context.py` 功能与用法（详细见脚本头注释）：

```bash
# 初始化上下文目录（000_Context/）+ 台账（项目根 问题清单.md）
python scripts/init_context.py <项目根>

# 同时创建一个问题文件夹（001-标题，含问题描述模板 + 附件/ + 证据/）
python scripts/init_context.py <项目根> --issue "001-问题精确描述"

# 对散放文件做启发式归类（*.slx→01_Model、*_autosar_rtw/*.c/*.h→02_Code、
# *.docx/*.pdf→03_Requirement、*.sldd→05_Calibration 等；不确定的列出让用户决定）
python scripts/init_context.py <项目根> --organize <待归类目录>
```

- 上下文目录已存在时不会重建，只报告缺失的子目录。
- 命名不规整的通用上下文由 agent 主动归类（第 0 步第 2 点），`--organize` 是可选辅助。
- `--issue` 创建问题文件夹：从 `assets/issue-folder-template/` 读取模板生成 `问题描述.md`（自动补全版，工程师无需填写，排查开始时由 agent 填充），复制 `附件说明.md` 到 `附件/`，再建 `证据/` 空目录。

## 六、通用陷阱

- 上下文冲突仲裁（与第 0 步一致）：模型与代码是"实现真相"、优先级最高；模型与生成代码版本不一致时，**以生成代码（实际刷写软件）为准**；需求/接口/标定/日志与实现冲突时以模型和代码为准，报告中注明版本和构建时间，冲突点列入遗留确认点。
- 生成代码里的中间信号（示例：空调项目的 `LogicalOperator*`/`Switch2_*`）是无业务名临时变量，必须读赋值/使用上下文判断语义，不能直接引用当结论。
- 同一触发/更新信号可能被多个功能共用，定位显示/状态类问题时先查共用。
- 代码注释可能是 GBK 编码，grep 中文乱码属正常，改用英文关键字或按行号读。
- 车型/配置差异（如 5S/6S、`Configure_*` 参数）：先查关键路径有没有配置分支，没有则各配置行为一致，可一并下结论。
- 外部控制器/面板的联动行为（模块内部看不到触发来源）要归到"其他"层并列入遗留确认点。
