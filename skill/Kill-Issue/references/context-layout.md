# 上下文目录约定（通用上下文 + 问题文件夹 + 台账）

## 一、总体布局（编号体系）

```
<项目根>/
├── 000_Context/                      # 通用上下文（所有问题共享，编号 000）
│   ├── 01_Model/                     # Simulink 控制模型
│   ├── 02_Code/                      # 模型生成的代码包
│   ├── 03_Requirement/               # 需求文档
│   ├── 04_Interface/                 # 接口信号表 / ARXML / DBC
│   ├── 05_Calibration/               # 标定文件
│   ├── 06_Test/                      # 测试环境说明
│   └── 07_Logs/                      # 共享日志/报文（可选）
├── 001-问题精确描述/                 # 问题 001（与上下文平级）
│   ├── 问题描述.md                  # 由排查 agent 自动补全（工程师无需填写）
│   ├── 附件/                         # 该问题的专属上下文：logs、测试录制文件、
│   │                                 #   报文、截图 —— 只用于本问题，不进通用上下文
│   ├── 证据/                         # 排查过程截图、代码摘录
│   └── 根因分析报告.md               # 报告（按类型命名：根因分析/通用排查/5W/8D/定位简报）
├── 002-问题精确描述/
├── 003-问题精确描述/
└── 问题清单.md                       # 台账（项目最外层，汇总所有问题状态）
```

> 兼容说明：已有工程（如 `ModelandCode_SOP_3/`）本身就是通用上下文，不强制改名成 `000_Context`，只要内部能对应到下列 7 类材料即可。初始化脚本会识别已存在的目录，不重复创建。

## 二、规整（初始化动作）

用户放入的通用上下文**命名不规整**时，agent 主动按类别归类到 `000_Context/` 的子目录：

- 依据文件类型/内容判断类别（*.slx → 01_Model；*_autosar_rtw/、*.c、*.h → 02_Code；需求类文档 → 03_Requirement；接口表/ARXML/DBC → 04_Interface；*.sldd/*.a2l → 05_Calibration；测试说明 → 06_Test；日志/报文 → 07_Logs）。
- 移动后**报告归类结果**（来源 → 目标）；不确定类别的文件问用户，不擅自挪动。
- 脚本可选辅助：`init_context.py --organize <目录>` 做启发式归类。

## 三、上下文 7 类材料清单（第 0 步完整性检查用）

| 目录 | 内容 | 必需性 | 排查中的用途 | 缺失时的影响 |
|---|---|---|---|---|
| 01_Model | Simulink 模型 `*.slx`（及子系统 `*.xml` 描述） | **必须** | 定位逻辑错误、状态机、子系统层级；出模型截图 | 无法做模型层定位与截图，只能看代码 |
| 02_Code | 模型生成的代码包（如 `*_autosar_rtw/`） | **必须** | 以实际刷写软件为准定位代码块（文件+行号） | 无法定位生成代码；模型版本与刷写版本可能不一致 |
| 04_Interface | 接口信号表、ARXML（AUTOSAR 接口）、DBC（CAN 报文） | **条件必需**（问题附件含 log/报文时必给 DBC）+ 按需 | 报文 ID→信号名翻译、核对信号定义/报文周期/字节序 | 报文无法解析成信号、信号语义只能靠猜 |
| 03_Requirement | 需求文档（SRS、功能规范、变更单） | 按需（需求存疑/归因需要时） | 判定"预期行为"、需求是否定义不清/矛盾 | 只能凭产品意图推断预期，归因易存疑 |
| 05_Calibration | 标定文件（`*.sldd`、`*.a2l`、标定表） | 按需（标定/数值类问题需要） | 核对阈值、增益、下限、死区等标定值 | 标定类根因无法确认 |
| 06_Test | 测试环境说明（HIL/MIL 配置、车型/功能配置机制等） | 按需（区分测试问题需要） | 区分测试问题 vs 软件问题；判断配置差异 | 无法判定测试环境问题 |
| 07_Logs | 共享日志/报文 | 可选 | 时序证据、信号趋势、报错码 | 只能依赖问题附件中的日志 |

**第 0 步动作（分级，不需要 7 类给全）**：
- **必须项**（01_Model、02_Code）缺失 → 明确提醒补齐（阻塞）；
- **条件必需项**（04_Interface）：问题附件含 log/报文而缺 DBC → 明确提醒补齐（报文解析必需）；
- **按需项**（03_Requirement / 05_Calibration / 06_Test / 07_Logs）→ 按问题类型判断，排查中需要时再向用户要，缺失不阻塞。

**冲突仲裁**：上下文材料互相矛盾时，以**模型和代码**为准（实现真相，优先级最高）；模型与生成代码不一致时以生成代码（实际刷写软件）为准；需求/接口/标定/日志与实现冲突时以模型和代码为准，冲突点记入报告"遗留确认点/证据差异"。

## 四、问题文件夹与专属附件

- 命名：`三位序号-问题精确描述`（如 `003-XX 模式下 YY 执行器开度异常`），描述要能一眼看出问题对象与现象。**一个问题一个文件夹，处理完再开下一个。**
- `问题描述.md` **由排查 agent 自动补全**：工程师只需丢文件（logs/报文/截图/trace）+ 一句话描述，agent 提取信息填充，缺失项标记"待确认"并澄清补齐；模板见 `assets/issue-folder-template/问题描述.md`。也可以不建文件，问题直接由用户 prompt 输入。
- **`附件/` 是当前问题的专属上下文**：问题相关的 logs、CANoe/CANape 录制的报文（.asc/.blf/.mf4/.dat 等）、截图放这里，只用于当前问题，不混入通用上下文 `000_Context/`。解析方法见 [log-reading.md](log-reading.md)。
- 排查中产生的截图、代码摘录放 `证据/`。
- 报告命名：`根因分析报告.md` / `通用排查报告.md` / `5W分析.md` / `8D报告.md` / `定位简报.md`，按所选模板输出到问题文件夹根。

## 五、问题清单台账（项目最外层 问题清单.md）

放项目**最外层**，每完成一个问题登记一行：

| 编号 | 标题 | 状态 | 归属层 | 结论一句话 | 报告文件 |
|---|---|---|---|---|---|
| 001 | XX 执行器开度异常 | 已闭环 | 软件（标定/逻辑错配） | 模式强切导致标定下限失效 | 001-xxx/根因分析报告.md |
| 002 | XX 状态灯是否熄灭 | 待产品确认 | 其他（外部联动） | 外部请求连带触发状态退出 | 002-xxx/根因分析报告.md |

状态取值建议：排查中 / 待产品确认 / 待供应商确认 / 已闭环。当前问题登记完再处理下一个问题。
