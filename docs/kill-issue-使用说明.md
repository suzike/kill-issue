# kill-issue 使用说明

汽车软件问题排查 Skill —— 配套文件：`kill-issue.skill`（zip 包，即本说明对应的技能本体）。

## 一、这是什么

kill-issue 把"汽车控制器软件问题排查"固化为**通用标准流程**（不限于任何特定控制器、功能类型或问题类型），适用于：

- Simulink 控制模型或生成代码的行为异常（状态/模式/显示、按键或请求联动、控制逻辑、执行器、传感器等各类问题）
- HIL / MIL 测试失败、整车实验异常、标定问题
- 报错日志、CAN 通信与报文问题（CANoe .asc/.blf、CANape .mf4/.dat 等）
- 现象与预期不符、需要判定问题归属层（模型 / 软件 / 测试 / 需求 / 其他）

核心产出：**结构化排查报告**（根因分析 / 通用问题排查 / 5W / 8D / 轻量简报，用户可选）+ **问题台账**。

## 二、Skill 内容结构

```
kill-issue/
├── SKILL.md                          主流程（初始化并规整上下文→收集输入并自动生成问题描述→澄清→判定归属层→定位→选模板、出报告→登记）
├── scripts/init_context.py           初始化脚本（建上下文目录、台账、问题文件夹、文件归类）
├── references/
│   ├── report-rootcause.md           根因分析报告模板（默认推荐）
│   ├── report-general.md             通用问题排查报告模板（正式完整交付）
│   ├── report-5w.md                  5W 分析模板
│   ├── report-8d.md                  8D 报告模板
│   ├── report-brief.md               轻量定位简报模板
│   ├── context-layout.md             目录结构与上下文材料分级清单
│   ├── log-reading.md                CANoe/CANape 等日志解析指引
│   └── debug-methods.md              排查方法库（7 大套路 + 常见坑）
└── assets/issue-folder-template/     自动补全版问题描述与附件说明模板
```

## 三、安装方法

### 方式 A：Reasonix（推荐）

把 `kill-issue.skill` 放到本地，解压出 `kill-issue/` 文件夹，放到以下任一位置：

- **项目级**（仅当前项目生效）：项目根目录下 `.reasonix/skills/`
- **全局**（所有项目生效）：Reasonix home 的 skills 目录

也可以在 Reasonix 会话里直接说"安装这个 skill：<kill-issue.skill 路径>"，由 agent 自动处理。

### 方式 B：Claude Code / Anthropic 生态

解压后把 `kill-issue/` 文件夹放到：

- `~/.claude/skills/`（个人全局）或项目 `.claude/skills/`（项目级）

重启后生效。若安装工具校验名字要求全小写，把文件夹改名为 `kill-issue` 即可（内容不用改）。

### 方式 C：OpenAI 生态（Codex CLI / ChatGPT Agent Skills）

OpenAI 生态兼容 SKILL.md 规范（name + description frontmatter），可直接使用：

- **OpenAI Codex CLI**：把 `kill-issue/` 文件夹放到 `~/.codex/skills/`（全局）或项目 `.codex/skills/`（项目级），Codex 通过 AGENTS.md 自动加载
- **ChatGPT Agent Skills**：在支持 Agent Skills 的产品/界面中导入 `kill-issue.skill` 技能包
- 大小写校验不通过时改名 `kill-issue`（仅安装适配，正式名为 kill-issue）

### 方式 D：其他 agent

看是否支持 skills 规范（SKILL.md + YAML frontmatter）；不支持时，SKILL.md 本身可作为排查流程的方法论文档参考。

## 四、使用方法

### 1. 触发

- **自动**：对话中出现触发词即生效——问题排查、根因分析、bug、故障、异常、HIL、MIL、整车实验、标定、报错、logs、报文、现象不符、行为异常、状态不对、逻辑错误、通信异常、故障码 DTC、执行器、传感器、显示异常等。
- **手动**：直接说"用 kill-issue 排查这个问题"。

### 2. 首次使用：初始化项目结构

```bash
# 建通用上下文目录 000-context/（模型/代码/需求/接口/标定/测试/日志）+ 台账 问题清单.md
python scripts/init_context.py <项目根>

# 对散放文件做启发式归类（*.slx→模型、*.c→代码、接口表→接口、*.sldd→标定、报文→日志等；不确定的会列出）
python scripts/init_context.py <项目根> --organize <散放目录>

# 建问题文件夹（001/002/003 三级：描述+专属上下文 / 过程数据 / 报告+证据）
python scripts/init_context.py <项目根> --issue "001-问题精确描述"
```

### 3. 工程师输入方式（不需要填任何表单）

- 把问题文件丢进来：logs、CANoe/CANape 录制的报文（.asc/.blf/.mf4/.dat）、截图、trace，放入问题文件夹 `001/` 或直接拖入对话。
- 在输入框用自然语言描述问题，一句话即可（如"XX 模式下某执行器开度很小调不了"）。
- 其余全部交给 agent：它会自动提取信息补全 `001/问题描述.md`（现象/预期/复现条件/环境版本/文件清单），缺的信息会在开始排查前向你逐个澄清确认。

### 4. 项目目录约定（编号体系）

```
<项目根>/
├── 000-context/          # 通用上下文（所有问题共享）：01_Model 02_Code 03_Requirement
│                         #   04_Interface(接口表/ARXML/DBC) 05_Calibration 06_Test 07_Logs
├── 001-问题精确描述/      # 问题 001：001/描述+专属上下文(问题描述.md+logs)、002/过程数据、003/报告+证据
├── 002-问题精确描述/      # 问题 002
└── 问题清单.md            # 台账（最外层，每完成一个问题登记一行）
```

要点：

- 通用上下文统一命名为 `000-context/`（命名不规范时 agent 直接改名并按类别归类子目录）。上下文材料**分级**：模型、代码必须提供；问题附件含 log/报文时必须有 DBC（否则报文解析不了）；需求、标定、测试说明等按问题需要提供，**不需要 7 类给全**。缺必须项时 agent 会提醒补充。
- 问题附件（CANoe .asc/.blf、CANape .mf4/.dat 等）是**该问题的专属上下文**，放对应问题文件夹 `001/`，不进通用上下文。
- 问题串行处理：001 弄完、登记完，再开 002。
- 上下文材料互相冲突时，**以模型和代码为准**（模型 vs 生成代码不一致时以生成代码为准）。

### 5. 排查与报告

调用后 agent 会按流程执行：规整目录（统一 000-context、问题文件夹 001/002/003 分级、建问题描述.md+文件清单）→ 读上下文 → 全量扫描后苏格拉底式逐个澄清（每题 4 选项+推荐+可自定义）→ 判定归属层 → 定位证据（代码块带注释、模型子系统截图、需求/接口比对、日志时间线）→ 按所选模板出报告。

报告类型（未指定时按问题特征推荐默认）：

| 报告形式 | 适用场景 | 产物文件名 |
|---|---|---|
| 根因分析报告（默认） | 控制逻辑、状态/模式、显示、通信类问题完整技术排查 | 根因分析报告.md |
| 通用问题排查报告 | 任何类型问题的正式完整交付（对外汇报、项目总结） | 通用排查报告.md |
| 5W 分析 | 责任归属争议、摆清事实与责任方 | 5W分析.md |
| 8D 报告 | 量产/供应商质量问题的完整纠正流程 | 8D报告.md |
| 轻量定位简报 | 快速确认问题在哪一层 | 定位简报.md |

### 6. 台账登记

每完成一个问题，在项目最外层 `问题清单.md` 登记一行：编号 / 标题 / 状态 / 归属层 / 结论一句话 / 报告文件。

## 五、报告写作规范（skill 强制）

1. 结论先行：报告开头一句话结论 = 结论 + 根因 + 触发机制。
2. 图文并茂：关键机制配表格/流程图，模型与日志证据配截图。
3. 结构化语言：人类工程师能直接读懂；**头号禁令是禁止通篇堆砌软件/模型内部信号名与中间量**（如 Switch2_jh0、LogicalOperator1_dg），信号名出现必须配业务语义翻译；同时避免星号（***、★★）装饰与乱码符号。
4. 代码证据：文件 + 行号 + 代码块，逐块中文注释解释业务含义。
5. 信号名规范：出现中间信号名必须配语义翻译（示例：`Switch2_jh0` = "A/C 键按下检测结果"）。
6. 归因方向准确：谁触发谁、哪一侧先变，方向不确定写入"遗留确认点"。
7. 证据索引：报告尾部放"环节 / 语义 / 位置"三列表，方便复核。

## 六、常见问题

| 问题 | 处理 |
|---|---|
| 安装后不生效 | 确认文件夹名与路径正确（.reasonix/skills/ 或 ~/.claude/skills/）；大小写校验不过就改名为 kill-issue（仅安装工具适配，正式名为 kill-issue） |
| 模型与生成代码对不上 | 以生成代码（实际刷写软件）为准，报告中注明版本与构建时间 |
| 报文 ID 看不懂 | 需要 DBC/接口表（04_Interface），缺失时会让用户补充 |
| .dat/.rec 文件读不了 | 用 CANape 导出为 .mf4/.csv 再分析 |
| 日志中文乱码 | GBK/UTF-8 编码问题，代码文件同理，按需转码 |
